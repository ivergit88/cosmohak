# Алгоритмы

## 1. Граф сети (graph.py)

На каждом отсчёте `t` официальный `geometry.snapshot(scenario, t)` возвращает
рёбра `[id1, id2, distance_km]` (контакты двунаправленные):
- спутник–спутник: `dist < isl_range_km`, отрезок не пересекает Землю,
  оба активны;
- наземный пункт–спутник: `elevation ≥ min_elevation_deg`, спутник активен,
  для шлюза дополнительно он не в `gateway_outage`.

`build_link_graph` разделяет рёбра на межспутниковые (смежность) и наземные
линии; **наземные узлы не ретранслируют** — client может быть только
источником, gateway только терминалом.

## 2. Minimum hops (обязательная стратегия)

BFS из клиента по графу спутников:
1. Стартовые узлы — спутники, видимые клиентом (соседи по отсортированным ID).
2. Расширение — только через межспутниковые рёбра; шлюз никогда не помещается
   в очередь (он терминал).
3. При обработке спутника `u` все шлюзы, видимые от `u`, дают кандидата
   маршрута `(hops(u) + 1, порядок_обнаружения(u), u, шлюз)`; выбирается
   минимальный кандидат.

**Детерминизм.** В BFS с FIFO и отсортированной смежностью порядок первого
обнаружения узла совпадает с лексикографическим порядком его кратчайших
путей (доказывается индукцией по слоям: у узлов одного слоя пути сравниваются
так же, как их родители, плюс ID на последней позиции). Поэтому
«первый обнаруженный» = «лексикографически наименьший», и правило
`(дистанция, порядок, ID шлюза)` даёт полностью воспроизводимый маршрут.

Маршрут клиента восстанавливается по дереву родителей:
`client → s1 → … → sk → gateway`; `hops = k + 1` рёбер (две наземные линии
включены), длина — сумма `distance_km` рёбер.

## 3. Minimum geometric distance (альтернативная)

Релаксация по ключу `(длина_км, hops, кортеж_пути)`:
- старт: видимые спутники с ключом `(d_наземной, 1, (client, sat))`;
- релаксация межспутниковых рёбер до стабилизации (веса > 0, циклы не
  улучшают ключ);
- финализация: добавление наземной линии к шлюзу; минимум по всем шлюзам.

Ключ лексикографичен и монотонен при расширении пути, поэтому алгоритм
воспроизводим. Достижимость (availability) обязана совпадать с BFS — это
проверено тестом на сценарии 01. Стратегия меняет только конкретный путь;
утверждений о физическом «превосходстве» не делается.

## 4. Резервный путь

Повторный min-hops BFS с `forbidden = внутренние спутники основного
маршрута`. Клиент и шлюз могут совпадать. Доля отсчётов, где резерв
существует, — метрика `backup_fraction`.

## 5. Валидация маршрута (validate_path)

Каждый путь проверяется: источник — запрошенный client; терминал — gateway;
внутренние узлы — активные спутники; каждое звено существует в
`snapshot.edges` (двунаправленно); шлюз не в outage; циклов нет.
Используется в debug-режиме расчёта и в тестах экспорта («каждый
сохранённый path валиден в свой t»).

## 6. Метрики (metrics.py)

- `visibility_fraction` = отсчёты с ≥1 видимым активным спутником / все отсчёты.
- `availability_fraction` = отсчёты с полным маршрутом / все отсчёты.
- Перерывы — серии подряд идущих отсчётов без маршрута; границы серий
  переводятся в секунды (`первый_отсчёт … последний_отсчёт + step`), серии
  в начале и конце периода учитываются. `max_outage_s` — максимум серий.
- Причина интервала — приоритетная (минимальный код) среди категорий,
  присутствовавших в серии; полный состав — в `reasons`.
- Статистика маршрутов: mean/median/p95 (nearest-rank)/max hops; смены
  маршрута — сравнение путей соседних «подключённых» отсчётов (переходы
  в перерыв не считаются сменой); средняя длина км; `backup_fraction`.

## 7. Диагностика причин (simulation + routing)

Порядок проверки на отсчёте:
1. `NO_VISIBLE_CLIENT_SATELLITE` — нет видимых активных спутников;
2. `GATEWAY_UNAVAILABLE` — все шлюзы в `gateway_outage`;
3. `NO_GATEWAY_CONTACT` — онлайн-шлюзы не видят ни одного активного спутника;
4. `ISL_NETWORK_DISCONNECTED` — оба контакта есть, пути через ISL нет.
Для нескольких шлюзов — поблочная сводка в деталях статуса.

## 8. Критичность (resilience.py)

Виртуальный отказ каждого спутника на весь горизонт **без пересчёта
геометрии**: один проход по отсчётам; если в основном маршруте клиента
спутника нет — маршрут остаётся допустимым (клиент не страдает), если есть —
повторный BFS достижимости без этого узла. Считаются: Δmin/Δmean
доступности, рост худшего перерыва (базовые перерывы объединяются с новыми
потерями), затронутые клиенты, использование в маршрутах. Ранжирование:
Δmin ↓, затем Δхудшего перерыва ↓.

## 9. Быстрый подбор конфигурации (optimizer.py)

Детерминированный (seed фиксирован) поиск по осям RAAN/фазирование:
несколько случайных мульти-смещений + координатный спуск со шагами
±7.5/15/30/60°, нормировка mod 360. Оценка кандидата — расчёт на
прореженной сетке (шаг ×4); критерий — лексикографический ключ
(max min-доступность → max mean-доступность → min худшего перерыва →
min средних hops). Бюджет ограничивается слайдером (8–60 оценок);
лучшая конфигурация пересчитывается на полной сетке. `launch_batch`
не изменяется.
