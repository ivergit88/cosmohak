# Допущения и принятые решения

Все допущения приняты консервативно и проверены тестами. Порядок
авторитетности: официальные PDF/JSON/`geometry.py` → ответы экспертов →
инженерные улучшения.

## Модель и геометрия

1. **Геометрия — только официальная.** Все расчёты берут координаты,
   активность, рёбра и углы из `vendor/geometry.py` (без изменений).
   Параллельный движок по формулам «Описание данных» совпадает с ним
   в тестах parity (координаты, active, рёбра, elevation; допуск 1e-7).
2. **`earth_angle0_deg` не влияет на контакты.** В официальном
   `snapshot` контакты считаются в инерциальных координатах, а наземные
   точки не поворачиваются; угол поворота Земли применяется только к
   «земным» координатам, которые в контактах не используются. Мы
   воспроизводим поведение официального модуля буквально и показываем
   3D-сцену в той же системе (наземные пункты неподвижны).
3. **Сетка времени**: `range(0, horizon_s, step_s)`, правый конец не
   включается (720 отсчётов для 86400/120). Число тиков нигде не
   захардкожено.
4. **Границы отказов `[start_s; end_s)`**: начало включается, конец
   исключается — как в «Описании данных» (пример [21600; 43200) = 6-й час).
   Покрыто тестами «активен до/неактивен в start/активен ровно в end».

## Маршрутизация

5. **Детерминизм не регламентирован кейсом.** Допустимых маршрутов может
   быть несколько, эталонного пути нет. Выбор маршрута — часть качества
   алгоритма: по умолчанию берётся путь с минимальной суммарной
   геометрической длиной (взвешенный поиск кратчайшего пути, ключ
   «длина км → число рёбер → путь»), при полном равенстве —
   лексикографически наименьший. BFS «минимум рёбер» доступен как
   baseline; достижимость стратегий идентична (проверено тестом).
6. **Число переходов (hops)** = число рёбер маршрута, включая две наземные
   линии; при отсутствии пути значение отсутствует («—»).
7. **Смена маршрута** считается только между соседними «подключёнными»
   отсчётами; переходы «маршрут ↔ перерыв» фиксируются как перерывы, не
   как смены.
8. **Резервный путь** — node-disjoint по внутренним спутникам (клиент и
   шлюз могут совпадать). Это аналитическая метрика, на availability не
   влияет.
9. **min_hops (BFS)** — baseline-альтернатива в интерфейсе: достижимость
   совпадает с min_distance (тест), конкретный путь может отличаться.
   Превосходства одной стратегии «физически» не утверждаем — оптимизируется
   одна прозрачная метрика, суммарная длина доступных линий.

## Метрики и диагностика

10. **p95 hops** — методом ближайшего ранга (nearest-rank): элемент с
    индексом ⌈0.95·n⌉.
11. **Приоритет причины перерыва** — первая применимая категория из
    постановки: нет видимого спутника → шлюз в outage → нет контакта шлюза →
    разрыв ISL. В интервале перерыва причиной указывается категория с
    наивысшим приоритетом среди присутствовавших, полный состав — рядом.
12. **90%** — целевой ориентир: показывается линией и флагом «цель
    достигнута», но конфигурация не объявляется невалидной при
    недостижении (позиция подтверждена экспертами).

## Интерфейс и экспорт

13. **Порядок routes в экспорте** — по отсчётам, внутри отсчёта — клиенты
    в порядке файла; каждая пара `(t_s, client_id)` встречается ровно один
    раз (тест: 2160 записей для сценариев с 3 клиентами).
14. **Допустимость пустого path** — официальный формат: `path: []` при
    отсутствии маршрута.
15. **Оптимизатор** — бонус-модуль: coarse-сетка (шаг ×4) для скрининга,
    полный пересчёт лучшего кандидата; `launch_batch` не меняется; budget
    ограничен (8–60 оценок); seed фиксирован → воспроизводимость.

## Регрессионные числа

Регрессионный базлайн (наш движок, официальный `geometry.py`, сетка 720
отсчётов; формат: видимость/маршрут/макс. перерыв):

| Сценарий | C65 | C70 | C72 |
|---|---|---|---|
| 01 full | 704/696/480 | 719/711/120 | 720/712/120 |
| 02 first launch | 275/196/34320 | 351/114/39480 | 421/91/47760 |
| 03 outages | 609/571/1440 | 650/582/1440 | 670/594/1200 |
| 04 isl 2000 | 704/558/5640 | 719/448/10680 | 720/469/240 |

Для сценариев **01 и 02** значения совпадают с внешней контрольной
таблицей полностью (и по видимости, и по доступности, и по перерывам).

Для сценариев **03 и 04** наблюдались расхождения с той таблицей:
03 — на 1 отсчёт по двум клиентам (582/595 вместо 583/595… т.е. 0.14 п.п.),
04 — более заметное (наша доступность ниже: 77.5/62.2/65.1% против
83.6/73.2/75.3%). Проведён систематический поиск причины по чек-листу
(сетка, границы отказов, активный состав, видимость, рёбра, валидность
маршрутов, логика max outage):

- все 12 значений **видимости** всех четырёх сценариев совпадают с таблицей
  точно → видимость и активный состав считаются идентично;
- все значения **max outage** сценариев 01–03 совпадают точно (в 04
  совпадает C72: 240 с);
- сценарий 03 отличается от 01 только отказами; наши границы подтверждены
  тестами и совпадением C65 (571);
- рёбра берутся из официального `snapshot` без преобразований; каждый
  сохранённый путь валидируется по `snapshot.edges` (0 нарушений на
  4×720 тиках);
- перебор альтернативных правил (строгие/нестрогие неравенства, учёт
  блокировки Земли — при 2000 км блокировка недостижима математически,
  дистанция по поверхности, другие значения дальности 2000–3000) не
  воспроизводит табличные числа 04 ни одной комбинацией.

Вывод: контрольная таблица для 03/04 получена генератором с slightly иной
моделью связей, чем официальный `geometry.py` в поставке. Наш движок
следует официальному модулю и документу; таблица используется только как
внутренний регрессионный ориентир там, где она совпадает (01, 02, видимость
и перерывы 03). Числа зафиксированы в `tests/test_regression_fixtures.py`.
